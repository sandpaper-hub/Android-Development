В Android-разработке архитектурные подходы — это не «жёсткие правила», а набор практик, которые помогают сделать код читаемым, поддерживаемым и тестируемым.

---

## 🔹 Основные архитектурные подходы в Android

### 1. **MVC (Model-View-Controller)**

📌 Старейший подход, пришёл из классического UI.

- **Model** → данные и бизнес-логика.
    
- **View** → отображение (Activity/Fragment/Layout).
    
- **Controller** → связывает Model и View.
    

⚠️ Минусы: В Android часто Activity или Fragment становятся и View, и Controller одновременно → «God Object», сложно поддерживать.

---

### 2. **MVP (Model-View-Presenter)**

📌 Популярен в 2015–2018 годах.

- **Model** → данные (репозитории, API).
    
- **View** → только отображение, интерфейс.
    
- **Presenter** → управляет логикой, вызывает Model, передаёт данные View.
    

⚠️ Минусы: Presenter всё равно может разрастаться, нет явной поддержки жизненного цикла.

---

### 3. **[[MVVM]] (Model-View-ViewModel)** ✅ (рекомендуемый Google)

📌 Сейчас де-факто стандарт. Особенно удобен с Jetpack Compose.

- **Model** → бизнес-логика, репозитории, источники данных.
    
- **View** → UI (в Compose — Composable функции).
    
- **ViewModel** → хранит состояние UI, управляет данными, переживает конфигурацию.
    

Пример:

- View подписывается на `StateFlow`/`LiveData`.
    
- ViewModel меняет данные.
    
- UI автоматически перерисовывается.
    

---

### 4. **MVI (Model-View-Intent)**

📌 Ближе к «чисто реактивному» стилю.

- **Model** → состояние всего экрана (immutable data class).
    
- **View** → UI, подписывается на состояние.
    
- **Intent** → действия пользователя (клик, свайп, ввод текста).
    

Принцип:

```
Intent (событие) → Reducer (обновление Model) → новое состояние → View
```

⚡️ Пример: Orbit MVI, Maverick, Redux-подходы.  
⚠️ Минусы: многословность, boilerplate.

---

### 5. **Clean Architecture (Onion, Uncle Bob)**

📌 Архитектурный стиль, не завязанный на Android.  
Уровни:

1. **Entity (бизнес-модель)**
    
2. **UseCase / Interactor (бизнес-правила)**
    
3. **Interface Adapter (ViewModel, репозитории)**
    
4. **Framework & UI (Compose, Room, Retrofit и т. д.)**
    

Идея → зависимости направлены **от внешнего к внутреннему**.  
⚡️ В Android часто используют как «надстройку» над MVVM или MVI.

---

### 6. **Unidirectional Data Flow (UDF)**

📌 Принцип, а не архитектура.

- Состояние течёт в **одну сторону**: ViewModel → UI.
    
- UI посылает события → обратно в ViewModel.
    
- Нет «двустороннего связывания» (как в Data Binding).
    

Compose идеально поддерживает UDF.  
Пример: `val state by viewModel.uiState.collectAsState()`

---

### 7. **Redux-подходы (частный случай MVI)**

📌 Применяют идеи Redux/Flux (из React-мира):

- Один глобальный Store с состоянием.
    
- Reducer меняет состояние.
    
- View подписывается на часть Store.
    

В Android → редко в чистом виде, но Orbit, ReKotlin, Jetpack Compose-эксперименты.

---

## 🔹 Какой выбрать?

- **Учишься / делаешь pet-проекты** → MVVM (самый простой и понятный).
    
- **Большое приложение, много разработчиков** → MVVM + Clean Architecture.
    
- **Хочешь реактивный и «функциональный» подход** → MVI.
    
- **Эксперименты или очень сложные состояния** → Redux-подходы.
